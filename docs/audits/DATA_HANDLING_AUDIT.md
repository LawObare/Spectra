# SPHEREx Data-Handling Audit

**Reviewed:** 2026-11-12  
**Scope:** Supplied public SPHEREx repositories/tutorials and Spectra's current ingestion, time-domain, and spectrum paths. This is an evidence-based audit and change proposal; it does not change the immutable SPECIFICATION.md or implement processing changes.

## Summary

The data path preserves several important release-product properties: MEF extensions are parsed by name, live cutouts are rejected unless image, variance, flags, and WCS-WAVE are present, temporal wavelength matching precedes reprojection, and flux/variance are coadded with inverse-variance weighting. The main correctness risks are incomplete collection coverage, exposure thinning in the time-domain path, a fixed pixel-solid-angle assumption in absolute photometry, and unverified overlap between releases. The main performance plan is directionally sound, but cache and latency claims need sustained measurement.

## Findings

| Priority | Finding | Evidence and impact | Proposed correction |
|---|---|---|---|
| P1 | Deep-survey collections are not accepted by the live ingest allowlist. | IRSA's [intro tutorial](https://caltech-ipac.github.io/irsa-tutorials/spherex-intro/) lists spherex_qr2, spherex_qr2_deep, spherex_qr3, and spherex_qr3_deep. Spectra's default is QR2 + QR3 wide only and its validation rejects all other collection names ([ingest.py](../../backend/science/ingest.py#L61), [ingest.py](../../backend/science/ingest.py#L962)). This excludes deep-field coverage even when IRSA has it. | Decide whether deep products are in the supported product scope. If yes, add them through a validated collection registry and preserve wide/deep and release provenance end-to-end. If no, state “wide-survey only” in the UI and API. Do not silently combine deep and wide products. |
| P1 | SIA freshness is not represented in coverage results. | The tutorial says archive ingestion is weekly and SIA availability can lag by about a day. Spectra caches SIA query results for 600 seconds ([ingest.py](../../backend/science/ingest.py#L79), [ingest.py](../../backend/science/ingest.py#L118)). A zero-row query therefore means “no coverage reported by this collection/query at this time,” not necessarily “no observation exists.” | Record query time, collection, and release with coverage results. Make no-coverage messaging distinguish archive-reported absence from a stale or incomplete archive view. Keep cache invalidation tied to query identity and TTL. |
| P1 | Time-domain ingest deliberately keeps only one exposure per pass and detector. | The ingest code selects the exposure closest to the median MJD for each pass/band in normal mode, while spectrum mode retains every recognized exposure ([ingest.py](../../backend/science/ingest.py#L1040)). This reduces requests and time, but discards repeat measurements before coaddition and may reduce depth or alter variance. | Keep this as an explicit fast-preview policy if latency requires it. For science-quality stacks, retain all accepted exposures and coadd by pass/band; show the exposure count and preview/full-stack state so the sampling choice is visible. Benchmark both paths. |
| P1 | Absolute flux conversion assumes a constant square 6.2-arcsecond pixel. | Spectra's spectral extraction derives pixel solid angle from a fixed 6.2-arcsecond scale ([wave.py](../../backend/science/wave.py#L67)). The IRSA source-discovery example uses the solid-angle pixel map (SAPM) when converting surface brightness into point-source flux ([demo, flux and SAPM workflow](https://caltech-ipac.github.io/irsa-tutorials/spherex-source-discovery-tool-demo/)). A nominal pixel scale is not evidence that every detector pixel has identical solid angle. | Compare the current constant-area flux and variance against SAPM-based conversion at representative detector positions and wavelengths. If the difference is material, use the matching release SAPM and propagate its area factor into both flux and variance. Keep an explicit method/provenance field. |
| P1 | Combining QR2 and QR3 needs a duplicate-observation audit before all-exposure extraction. | Spectra queries configured collections concurrently and merges their exposure rows; spectrum mode then keeps all recognized exposures ([ingest.py](../../backend/science/ingest.py#L991), [ingest.py](../../backend/science/ingest.py#L1043)). The current spectrum endpoint extracts from all observations returned and records release and exposure IDs ([spectrum.py](../../backend/api/spectrum.py#L96), [spectrum.py](../../backend/api/spectrum.py#L107)). Reprocessed releases may overlap, but the reviewed code path does not show a release-preference/deduplication step before extraction. This is a risk to verify, not yet a proven duplicate-data bug. | Compare QR2/QR3 SIA rows by stable observation identity for overlapping sky/time samples. If duplicates exist, define a release-preference policy and deduplicate before wavelength-channel accumulation; retain rejected and selected IDs in provenance. |
| P2 | The source-discovery notebook is useful as a workflow example, not as a normative science contract. | It demonstrates SIA/TAP search, cloud access, source finding, photometry, SAPM usage, and bounded parallel downloads. It also labels some collection and SAPM identifiers as ephemeral. Its D2–D4 subtraction is a color/source-detection operation, not a temporal difference. Its sample FLAGS masks use exact values and include a likely detector-mask typo ([tutorial](https://caltech-ipac.github.io/irsa-tutorials/spherex-source-discovery-tool-demo/)). | Keep Spectra's wavelength-matched temporal-difference guard. Use current release flag definitions and bitwise masks; do not copy the notebook's literal flag comparisons or stale collection constants. |
| P2 | Public-products forecasts are not calibrated image data. | The [Public-products README](https://github.com/SPHEREx/Public-products/blob/master/README.md#L2-L10) describes forecast sensitivity/FWHM and simulated schedules, including 96-channel forecast assumptions. Spectra's live path processes release MEFs and its spectrum path uses 102 channels. | Cite the repository for mission-design context only. Do not use forecast sensitivity, channel count, or pixel-scale assumptions as an empirical noise model, release calibration, or detection threshold without separate reconciliation. |
| P2 | The SSDC pipeline is valuable processing context but not a drop-in dependency. | The [pipeline repository](https://github.com/Caltech-IPAC/spherex-pipelines) identifies itself as SSDC Level 1–3 production software and describes infrastructure-specific operation. Its change history documents memory-aware practices such as reusing PSF/wavelength products and avoiding large simultaneous allocations. | Study algorithms and memory practices, but keep Spectra's runtime contract based on public IRSA products. Adopt an algorithm only after matching its inputs, calibration level, and release semantics. |
| P2 | Performance evidence does not yet show which processing stage dominates live latency. | The current plan says cache hit rates and cold/warm latency remain unmeasured, and recommends 20 cold and 20 warm runs for three targets ([PROCESSING_OPTIMIZATION_PLAN.md](../planning/PROCESSING_OPTIMIZATION_PLAN.md#L3-L20)). Fetching is bounded to four archive operations and gathers selected cutouts concurrently ([ingest.py](../../backend/science/ingest.py#L1082)). | Collect stage timing, bytes per HDU, exposure count, cache state, and result dimensions for cold and warm runs. Tune concurrency and S3 range size from these results; the tutorial's eight-thread example is not evidence that eight is safe for this service. |

## Data invariants to retain

1. Treat Level-2 IMAGE as calibrated surface brightness in MJy/sr. The IRSA intro tutorial explicitly says the ZODI model is not subtracted from IMAGE; do not silently subtract it.
2. Preserve IMAGE, FLAGS, VARIANCE, ZODI, PSF, WCS-WAVE, and their headers when the caller needs them. The current parser records these extensions, and the time-domain path requires IMAGE, FLAGS, VARIANCE, and WCS-WAVE before processing ([ingest.py](../../backend/science/ingest.py#L788), [cutout.py](../../backend/api/cutout.py#L448)).
3. Use the astrometric WCS for sky reprojection and the spectral WCS/WCS-WAVE solution for wavelength assignment. The tutorial documents separate astrometric, pixel-coordinate, and wavelength WCS representations. Do not replace those with a detector-wide constant wavelength.
4. Preserve 32-bit FLAGS semantics through reprojection and coaddition. Bit tests must use the official flag definitions; exact-value comparisons can accidentally discard pixels with multiple bits set.
5. Keep provenance attached to every result: collection/release, exposure IDs, MJD coverage, selected processing method, source badge, and whether the result is a preview or full stack.

## Recommended implementation order

1. **Close the product-scope gap:** explicitly decide wide-only versus wide+deep; make the API, UI labels, configuration validation, and benchmarks agree.
2. **Verify overlap and measurement depth:** quantify duplicate QR2/QR3 observations and compare current one-exposure previews with all-exposure pass stacks.
3. **Validate absolute photometry:** compare fixed-area and SAPM conversions, including variance propagation, before changing flux outputs.
4. **Measure before performance tuning:** persist the cold/warm stage breakdown and archive byte counts already described in the optimization plan; tune the largest measured stage.
5. **Update contracts after validation:** record accepted collection names, release precedence, WCS/units, masks, and provenance in operational documentation. Keep SPECIFICATION.md unchanged unless the project owner explicitly revises its immutable contract.

## Source notes

- The MPIA repository is a Hack Day script/notebook collection. Its variance discussion is a warning that some prior cutout workflows omitted variance, not a recommendation to replace available release variance.
- Public-products forecasts use a different design context from public QR release MEFs; their 96-channel figure must not override the release-specific 102-channel extraction contract.
- The source-discovery demo is community workflow code. Its useful operational patterns are SIA/TAP metadata handling, cloud access, caching, controlled parallel downloads, and SAPM-aware flux conversion; its sample-specific color and mask logic requires independent scientific validation.
